# 全站学习结构统一设计

## 状态

- 用户已批准把 Veto 样板推广到全站，并同时整理视频列表、视频详情、效果器索引和效果器详情四类界面。
- 全站继续保留“视频案例 / 效果器”双索引，不合并成混合信息流。
- 学习框架保持统一，职责和章节数量按内容自适应，不把所有视频硬套成 Veto 的固定数量。
- 内容采用“规则生成草稿 + 逐条证据复核”的方式整理。
- 全部内容完成并通过统一验收后一次性上线，不发布中间批次。

## 当前基线

- 当前站点包含 85 条视频、964 个已复核步骤。
- Veto 视频 `3JjAK2uhxM4` 是唯一已经具有学习地图和四段式步骤的记录。
- 其余 84 条视频、947 个步骤仍使用旧版快速结论和步骤展示。
- 当前站点已有视频时间点、截图、效果器案例、站内中文字幕、术语表、深链接和 GitHub Pages 发布链路。

执行期间如果新增视频，最终覆盖门槛按届时站点的全部记录计算，不允许只满足本规格记录的 85 条基线。

## 目标

1. 让读者在进入细节前先理解每条视频的设计目标、声音职责、关键决定和最终结构。
2. 把长步骤列表重组为可理解的设计章节，并让每一步直接说明输入、问题、动作和结果。
3. 让效果器页面优先回答“什么情况下用、解决什么问题、如何处理、会得到什么结果”。
4. 保留全部已复核干货、时间点、字幕、截图和证据，不用简洁展示替代底层事实。
5. 统一四类主要界面的信息层级、控件和视觉语言，同时保留现有路由、播放与字幕能力。
6. 通过结构化校验和真实浏览器验收，确保全站一次性上线时没有半成品记录。

## 非目标

- 不增加练习、作业、评分、难度、预计学习时长或课程化文案。
- 不把参数数值、预设或固定范围放入主要学习层。
- 不重新翻译或改写整套字幕。
- 不下载或自行托管 YouTube 视频。
- 不改变效果器截图的证据归属，不用相似产品或同类效果器截图代替。
- 不建设新的营销首页、账户系统、云端数据库或内容管理后台。

## 信息架构

### 全站外壳

- 保留紧凑顶部栏、站点统计和“视频案例 / 效果器”分段切换。
- 两个索引分别维护自己的搜索、分类、用途筛选和排序状态。
- 不新增中间落地页；打开站点后直接进入可使用的视频索引。
- 保留现有哈希路由、视频时间参数、章节深链接和返回位置。

### 视频列表

每张视频卡片优先显示：

- 视频标题与来源。
- 一句话设计目标。
- 最重要的声音职责，数量受卡片空间限制但不改变详情数据。
- 章节数量、步骤数量和内容分类。

卡片不展示大段摘要、参数或完整步骤。搜索仍可命中卡片未展示的学习地图与步骤内容。

### 视频详情

固定阅读顺序为：

1. YouTube 播放器和站内中文字幕。
2. “30 秒读懂”：设计目标、职责、关键决定和最终结构。
3. 自适应设计章节与章节内步骤时间跳转。
4. 每一步的输入、问题、动作和结果。
5. 与本视频直接相关的效果器用法。
6. 术语、字幕全文和完整证据。

原始长描述与参数线索折叠在“查看完整说明”中。折叠只改变默认阅读密度，不删除内容；打印模式必须展开这些内容。

### 效果器索引

效果器卡片优先显示：

- 经统一命名的效果器名称。
- 最适合的输入或声音类型。
- 主要解决的问题。
- 最直接的处理结果。
- 已复核案例数量和属于该效果器的界面截图。

筛选以用途和声音目标为主，不以参数、厂商或插件链位置作为主要学习入口。

### 效果器详情

固定阅读顺序为：

1. 用法概览。
2. 适用输入。
3. 问题、动作和结果。
4. 适用边界与不应外推的内容。
5. 带来源视频、步骤、时间点和准确截图的案例。

同一效果器的多个案例可以归纳共同用途，但不能把单个案例的参数或结果提升为通用规则。

## 通用学习数据模型

### `learningMap`

每条视频记录都必须具有版本化学习地图：

```js
learningMap: {
  version: 1,
  goal: "一句话设计目标",
  roles: [
    { name: "声音职责", description: "该职责在本视频中的作用" }
  ],
  decisions: ["可迁移的关键设计决定"],
  sequence: "一句话最终结构顺序",
  chapters: [
    {
      id: "稳定章节标识",
      title: "章节标题",
      question: "本章解决的问题",
      summary: "本章处理结论",
      stepOrders: [1, 2]
    }
  ]
}
```

约束如下：

- `version` 必须为数字 `1`。
- `roles` 包含 3–6 个非空职责。
- `decisions` 包含 2–3 个非空决定。
- `chapters` 包含 2–5 个章节。
- 章节 `id` 在单条记录内唯一并保持稳定。
- `stepOrders` 必须完整、唯一地覆盖该记录的全部步骤序号。
- `goal`、`sequence`、章节标题、问题和总结都必须是简短事实句。

### 步骤 `learning`

每个步骤都必须具有：

```js
learning: {
  input: "本步处理的素材或声音层",
  problem: "素材进入动作或整组时暴露的问题",
  action: "作者采取的选择或处理动作",
  result: "处理后在画面、材质、力量、空间或辨识上的结果"
}
```

四个字段不得复制参数表，不得包含练习要求。视频没有单独说明处理前问题时，`problem` 必须明确写出“视频未单独说明处理前问题”，随后只能补充已确认的处理目的，不能推断作者动机。

## 内容证据规则

- 主要依据是现有已复核步骤、作者口述、画面确认和已经发布的效果器案例。
- 字幕用于定位和交叉检查；字幕措辞不能自动升级为已确认事实。
- 现有 `detail`、`params`、`effectUses`、截图、时间点和字幕记录保持原值，迁移只新增或更新学习层字段。
- 每条四段式描述都必须能回指到本步骤或本视频已有证据。
- 不确定的产品身份、插件作用或听感结论不得写入主要学习层。
- 效果器截图必须由严格的案例身份与步骤截图共同确认；无法确认时隐藏截图并保留文字证据边界。
- 一个视频截图资源不能同时代表两个不同效果器身份。

## 整理流程

### 1. 生成结构草稿

新增迁移工具通过 `tools/site-data.cjs` 的结构化解析接口读取记录，根据现有摘要、核心观点、步骤和已复核效果器案例生成候选学习地图与四段式字段。工具不得直接从自由文本进行全文件字符串替换。

### 2. 逐条证据复核

每条记录独立核对：

- 章节是否表达真实设计阶段，而非按步骤数量平均切分。
- 职责是否说明声音层在画面或听感中的工作。
- 四段式字段是否具体、简洁且不重复。
- 效果器名称、截图、步骤和时间点是否属于同一案例。
- 原始干货是否完整保留。

内部可按类别分组处理，但分组只是工作组织方式，不形成公开发布批次，也不需要用户逐组确认。

### 3. 原子写入

- 只有全部记录通过结构和证据检查后，迁移工具才写回站点数据。
- 写入使用临时文件和原子替换，失败时保留原始 `index.html`。
- 相同输入必须产生字节稳定的输出。
- 迁移报告列出全部记录、字段覆盖、证据警告和阻断错误。

## 渲染与兼容

- 将当前 Veto 身份专用的激活条件替换为 `learningMap.version === 1` 与通用结构校验。
- 所有三个视频详情渲染入口共享同一个学习数据投影，避免快速结论、章节和步骤采用不同有效性标准。
- 有效学习地图使用新版界面；任何结构异常在运行时整体回退旧版快速结论和步骤展示，不显示混合半成品。
- 最终发布门槛要求所有站点记录都通过新版校验，因此旧版回退只作为防御和未来导入保护。
- 搜索模型收录目标、职责、决定、章节和四段式步骤，并继续排除练习脚手架。

## 视觉与交互规则

- 使用紧凑、安静、适合重复查阅的知识库界面，不使用营销式 Hero、装饰性渐变或多层卡片。
- 卡片圆角不超过 8px；页面章节使用无框分区和清晰分隔线。
- 桌面端保留播放器侧栏；手机端播放器置顶并在激活后使用现有粘性逻辑。
- 章节时间按钮、步骤时间按钮、筛选控件和模式切换保持稳定尺寸。
- 视频和效果器卡片不因标签数量、长标题或异步状态改变整体布局。
- 中文长句、英文插件名和连续字符必须换行，不得造成横向溢出或内容重叠。
- 所有按钮、摘要和深链接具有上下文相关的可访问名称；键盘焦点进入正确区域。
- 截图优先显示完整、清晰、可识别的效果器界面，不做纯装饰裁切。

## 错误处理

- 单条记录出现空字段、无效章节、重复步骤、截图错配或证据缺失时，报告记录 ID、视频 ID、步骤序号和字段路径。
- 任何阻断错误都终止最终数据写入和发布，不跳过失败记录。
- 只有不影响事实准确性的展示性缺图可以作为警告；效果器身份不明、步骤缺失或学习字段无证据属于阻断错误。
- 运行时遇到不合法数据时整体回退该记录的旧版展示，并在自动化测试中暴露失败原因。

## 验证

### 数据与内容

- 全部站点记录具有 `learningMap.version === 1`。
- 全部步骤具有非空 `input`、`problem`、`action` 和 `result`。
- 每条视频的章节完整且唯一覆盖所有步骤。
- 迁移前后的原始描述、参数、时间点、字幕、截图和效果器案例深度相等。
- 主学习层不包含练习要求或参数表式描述。
- 效果器公开截图均通过严格身份与案例归属检查。

### 渲染与行为

- 自动渲染全部视频详情，验证学习卡、章节、四段式步骤、完整说明和播放器时间跳转。
- 验证视频和效果器搜索能命中新的学习字段，同时不会把参数或练习内容带入结果。
- 验证四类页面的路由、返回位置、字幕、全屏字幕、术语和深链接没有回归。
- 验证非法或部分学习地图完整回退旧版展示。

### 视觉与可访问性

- Playwright 遍历全部视频详情并检查桌面 `1440x1000` 与手机 `390x844` 的横向溢出、重叠和关键元素数量。
- 六个内容类别各选择代表视频进行桌面和手机截图审查。
- 视频列表、效果器索引和效果器详情分别进行桌面与手机截图审查。
- 打印模式展开完整说明并隐藏无意义的交互控件。
- 自动检查上下文标签、键盘焦点和目标唯一性。

### 仓库与发布

- 运行全部 Node、Python、便携包、确定性导出和 `git diff --check` 验证。
- 最终工作区必须干净，功能分支经过整合代码审查后才合并。
- 只在全部验收通过后一次性推送 `main`。
- 等待 GitHub Pages 工作流完成，并用缓存刷新参数验证公开首页、四类页面、代表字幕和截图资源。
- 公开验收必须确认部署提交等于本地与远端 `main` 的提交，不能从代码推送或排队状态推断发布成功。

## 完成标准

满足以下全部条件才视为完成：

1. 四类主要界面使用统一且自适应的学习结构。
2. 执行时站点的每条视频和每个步骤都通过新版内容校验。
3. 所有原始干货和证据完整保留，效果器截图归属准确。
4. 桌面、手机、打印、搜索、播放、字幕和深链接验证通过。
5. 全量测试与独立代码审查没有未解决的 Critical 或 Important 问题。
6. GitHub Pages 成功发布最终提交，公开浏览器验收通过。
